# 搜索引擎优化完整方案

## 文档定位

本文保存完整搜索方案，作为后续实施与验收基线。方案同时建设可离线工作的本地全文搜索和网易云、QQ 音乐多来源在线搜索。

折中方案（保留轻量本地匹配、在线搜索完全交给平台）不替代本文；若最终采用折中方案，应另行记录范围调整。

## 目标

- 在线页面继续支持网易云音乐、QQ 音乐来源切换。
- 搜索页支持“综合 / 本地 / 网易云 / QQ 音乐”搜索范围。
- 综合搜索并发查询本地索引、网易云和 QQ 音乐，单个来源失败不影响其他来源。
- 支持单曲、歌手、专辑、歌单和歌词分类搜索。
- 支持搜索历史、热搜、默认搜索词和输入联想。
- 支持中文子串、全拼、拼音首字母、本地歌词和可控的错字建议。
- 跨来源同一录音可以聚合，但不误合并现场版、翻唱、Remix 和伴奏。
- 默认排序符合音乐用户预期：先保证相关，再在同相关度层级内按标准化热度降序。
- 搜索索引属于可重建派生数据，任何索引故障都不得损害歌曲、收藏、歌单、下载或缓存关系。

## 当前实现基线

- 本地搜索逐首检查歌名、歌手和专辑，只支持前缀及包含匹配。
- 在线搜索已能并发请求网易云与 QQ 音乐，但只完整接入单曲搜索。
- 在线返回顺序基本沿用各平台，跨来源结果会受到请求完成先后影响。
- 歌手、专辑页主要来自本地结果整理，没有统一在线分类结果。
- 去重只依据 `(source, remote_id)`，不能识别两个平台上的同一录音。
- 没有历史、热搜、联想、歌词搜索、查询语法、统一热度和稳定跨来源排序。
- 高亮只处理第一个直接子串命中。

## 开源组件决策

### 直接使用

- SQLite FTS5（Public Domain）
  - Qt 6.11.1 的 `qsqlite.dll` 已确认包含 `ENABLE_FTS5`。
  - 提供 BM25、字段权重、前缀、短语、布尔、NEAR、高亮和 trigram 子串匹配。
- RapidFuzz C++（MIT）
  - 仅对 FTS5 召回的有限候选执行 Levenshtein、部分匹配和词序相似度计算。
  - 不用于全库暴力扫描，不静默替换用户查询。
- `mozillazg/pinyin-data` 与 `mozillazg/phrase-pinyin-data`（MIT）
  - 生成歌名、歌手和专辑的全拼及拼音首字母。
  - 词语数据优先处理多音词，单字常用音作为回退。

### 暂不直接使用

- cppjieba（MIT）
  - 可用于中文歌词分词和关键词抽取；第一阶段使用 FTS5 trigram 已能满足精确歌词片段搜索，暂不增加词典体积和加载成本。
- Meilisearch（MIT）
  - 参考其输入即搜、容错、字段排序和相关度规则，不运行额外搜索服务。
- Typesense（GPL-3.0）
  - 参考其筛选、分组、联邦搜索及歌曲搜索设计；不引入 GPL 服务端和额外 Windows 部署负担。
- Tantivy（MIT）
  - 功能完善，但会引入 Rust 工具链、C++/Rust FFI 和第二套索引格式，不采用。
- Xapian（GPL v2+）
  - 原生 C++，但许可证和中文支持边界不适合当前项目，不采用。

## 总体架构

### 数据隔离

使用两个数据库文件：

```text
library.db                 用户歌曲、收藏、歌单、下载和缓存关系
search-index.sqlite       可删除、可重建的本地搜索索引和在线搜索缓存
```

- 主数据库保持现有完整性检查、备份、WAL 和单实例规则。
- 搜索索引使用独立连接和后台工作线程。
- 搜索索引损坏时关闭连接、备份诊断信息、删除并重建索引，禁止修改主库。
- 搜索索引不参与歌曲关系恢复；主库恢复后重新生成索引即可。

### 本地索引结构

歌曲元数据索引至少包含：

- 稳定歌曲 ID、来源和远端 ID。
- 歌名、歌手、专辑、别名及规范化文本。
- 歌名/歌手/专辑全拼和首字母。
- 本地导入、缓存、永久下载、收藏等筛选字段。
- 播放次数和最近播放时间（只作弱排序信号）。

歌词按行建立派生数据：

- `song_id`
- 行号和时间戳
- 原文、翻译和规范化文本
- 歌词文件指纹或修改时间

元数据和歌词使用 FTS5 trigram 支持中文任意位置子串。少于 3 个字符的查询只匹配歌曲元数据，不扫描全量歌词；歌词搜索至少需要 3 个中文字符或等价长度文本。

### 增量同步

- 首次启动或索引版本变化时在后台全量构建。
- 歌曲新增、删除、元数据变化、歌词变化和来源状态变化时增量更新。
- 同步任务依据稳定歌曲身份和文件指纹去重。
- UI 先使用当前可用索引；重建期间继续提供在线搜索和轻量本地回退。

## 多来源在线搜索

### 统一接口

扩展来源能力和统一 DTO，不允许 UI 解析平台原始 JSON：

- `SearchCategory`：综合、单曲、歌手、专辑、歌单、歌词。
- `SearchSuggestion`：文本、类型、来源、稳定远端身份。
- `SearchResultItem`：统一标题、作者、封面、远端 ID、匹配字段、来源名次、可播放状态和平台热度信号。
- `SearchPageState`：每个来源独立的 offset/cursor、hasMore、loading、error 和 generation。

### 网易云

- 热搜详情。
- 默认搜索词。
- 输入联想和多重匹配。
- `/cloudsearch` 的单曲、专辑、歌手、歌单和歌词类型。
- 平台搜索名次、明确热度字段及歌手热门歌曲名次作为热度信号。

### QQ 音乐

包装服务增加稳定契约：

- `/v1/search/hot`
- `/v1/search/suggest`
- `/v1/search` 分类参数与分页状态
- Smartbox 综合结果

继续使用固定版本 SDK、固定响应夹具、未知字段兼容和 `{ok,data,error}` 包装。QQ 服务不可用时只禁用 QQ 搜索，不影响网易云、本地索引和历史。

### 请求管理

- 输入在线查询前进行约 300ms 防抖。
- 在线联想至少输入 2 个字符才请求。
- 每次查询增加 generation；迟到响应不能更新新查询。
- 支持来源级请求取消或中止网络回复。
- QQ 服务冷启动完成后只补搜 QQ，不重复请求网易云。
- 每个来源独立增量渲染、分页、失败和重试。

## 搜索范围与界面

### 在线内容页

推荐、排行榜、云歌单和账号内容继续使用：

```text
[网易云音乐] [QQ音乐]
```

### 搜索页

搜索范围独立保存：

```text
[综合] [本地] [网易云] [QQ音乐]
```

结果分类：

```text
[综合] [单曲] [歌手] [专辑] [歌单] [歌词]
```

本地状态筛选：

```text
[全部] [可播放] [本地导入] [已缓存] [已下载]
```

- 搜索框获得焦点且输入为空时显示历史、平台热搜和默认搜索词。
- 本地联想立即返回，在线联想异步补充并显示来源标签。
- 支持上下键选择、Enter 打开/播放、`Ctrl+K` 聚焦。
- 返回搜索页时恢复关键词、分类、筛选、滚动位置和各来源分页状态。
- 综合页分区显示最佳匹配、歌手、单曲、专辑、歌单和歌词，不把不同对象混成一个无结构列表。

## 排序方案

### 原则

不能直接比较网易云和 QQ 的原始热度或相关度数值。先用统一规则判断相关度层级，再在同一层级中按来源内标准化热度排序。

### 相关度层级

从高到低：

1. 歌名完全一致。
2. 歌名前缀一致。
3. 歌名包含关键词。
4. 歌手与歌名组合命中。
5. 歌手完全一致或前缀一致。
6. 专辑名称命中。
7. 全拼命中。
8. 拼音首字母命中。
9. 错字或近似匹配。
10. 歌词内容命中。

不同层级之间不允许仅凭热度跨越，避免无关热门歌曲压过精确结果。

### 热度标准化

热度信号优先级：

1. 平台明确返回的热度、播放或流行度字段。
2. 平台搜索结果名次。
3. 歌手热门歌曲接口名次。
4. 本地播放次数只作为个人弱信号，不冒充全网热度。

每个平台内部把热度或名次转换到统一百分位。缺少某一来源时按已有来源重新归一，不直接扣半；两个平台都排得很高时可增加很小的跨平台共识加成。

默认“综合”排序：

```text
相关度层级
  → 层级内标准化全网热度降序
  → 跨平台共识
  → 收藏/最近播放等弱个人信号
  → 稳定歌曲身份
```

可选排序模式：

```text
[综合] [热度] [最近播放] [本地优先]
```

“热度”模式仍保留最低相关度门槛。

## 跨来源同曲聚合

- 先判断是否为同一录音，再聚合来源版本。
- 候选键包含规范化歌名、主要歌手、版本标记和时长容差。
- 时长差默认不超过约 2～3 秒。
- `Live`、翻唱、Remix、伴奏、不同语言版等标记必须一致，否则保持独立结果。
- 不丢弃任何来源身份；聚合行可以展开选择网易云或 QQ 版本。
- 聚合结果的相关度取成员中最好的统一相关度，不把两个来源的相关度相加。
- 热度按来源内标准化结果综合，避免直接比较平台原始数值。
- 默认播放版本按永久下载、自动缓存、本地文件、在线可播放状态和用户来源偏好选择。
- VIP、DRM、403、地区或版权限制逐来源判断，不绕过限制；一个来源不可播放时可尝试同组的其他合法来源。

## 错字与高亮

- RapidFuzz 只对 FTS5 返回的前 100～200 个候选二次评分。
- 相似度未达到阈值时不显示纠错建议。
- 纠错以“是否要搜索……”呈现，不静默替换查询。
- 高亮返回所有直接命中区间，并显示“歌名匹配 / 歌手匹配 / 专辑匹配 / 拼音匹配 / 歌词匹配”。
- 歌词结果显示命中行和时间戳，可跳转播放。

## 缓存与主库写入

- 热搜缓存约 5 分钟。
- 输入联想缓存约 10 分钟。
- 在线搜索结果缓存约 15～30 分钟，并采用先显示缓存、后台刷新。
- 缓存键包含来源、规范化关键词、分类、分页和筛选。
- 浏览搜索结果时不立即把所有在线结果写入主歌曲库。
- 只有播放、收藏、加入歌单、缓存或下载时才把在线歌曲安全 upsert 到主库。
- 搜索缓存和索引均为派生数据，清理后不得影响用户关系。

## 实施阶段

### 阶段 1：索引基础设施

- FTS5 运行时探测。
- 独立 `SearchIndexService`、数据库版本和后台线程。
- 全量构建、增量同步、故障重建和索引状态测试。

### 阶段 2：本地完整搜索

- 文本规范化、拼音全拼和首字母。
- 元数据和歌词索引。
- 短查询回退、歌词时间戳、RapidFuzz 建议和高亮。

### 阶段 3：在线搜索契约

- 统一 DTO、来源能力、请求代次和来源级分页。
- 网易云热搜、默认词、联想和分类搜索。
- QQ 热词、Smartbox、分类搜索和固定夹具。

### 阶段 4：搜索交互

- 历史、热搜、联想、范围、分类、筛选和键盘操作。
- 来源独立加载/错误/重试和页面状态恢复。

### 阶段 5：排序、聚合和缓存

- 相关度分层、标准化热度、可选排序模式。
- 同曲聚合及版本展开。
- 在线缓存、延迟主库写入和性能优化。

### 阶段 6：稳定性与验收

- 故障注入、竞态、索引重建、主库隔离和 UI 卡顿检查。
- 运行现有全部自动化测试及新增搜索测试。
- 重新构建并启动正式应用。

## 测试与验收

- `zhoujielun`、`zjl` 等查询可以命中周杰伦。
- 多音词优先采用词语读音，单字回退稳定。
- 1～2 字查询不会扫描全量歌词，3 字以上歌词能返回命中行和时间戳。
- 索引删除、版本变化或损坏后可后台重建，主库歌曲、收藏、歌单和下载不受影响。
- 网易云或 QQ 单独失败时另一个来源和本地搜索继续工作。
- 快速连续输入、切换来源或切换分类时，旧回调不会覆盖新结果。
- 平台热度经过来源内标准化，热门精确结果优先，热门但弱相关结果不能越级。
- 同曲聚合不误合并现场版、Remix、伴奏、翻唱和不同录音。
- 聚合后的收藏、批量操作、下载和播放使用稳定歌曲身份。
- 搜索构建和查询不阻塞 UI，不因单张封面完成而重建整个页面。
- 搜索缓存清理不影响歌曲记录和用户关系。

## 工程量与提交约定

- 传统人工工程量约 9～14 个开发日。
- 建议按索引、拼音/歌词、在线契约、界面、排序/聚合/缓存、测试六个阶段实施。
- 每阶段代码完成后 commit 并 push 到 `origin/main`。
- 每次编译或测试失败记录到 `docs/HANDOFF.md`，包含错误、根因和可行解决方案；环境缺失时先向用户确认配置。
